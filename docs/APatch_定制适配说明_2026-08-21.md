# TEESimulator v4.0 定制 APatch 适配说明

## 基线与分支选择

- 上游基线：`JingMatrix/TEESimulator` 的稳定标签 `v4.0`。
- 定制分支：`ckb-apatch-v4.0`。
- 没有直接合并 `dev`/canary。`dev` 在 v4.0 之后仍持续变化，包含控制 socket、WebUI、日志读取等大范围修改，和本次 APatch 启动问题不是同一个边界。
- 后续如需上游功能，应按提交逐项审查、选择性移植，不能把整个 `dev` 直接覆盖到已验证的定制启动链。

## 根因

TEESimulator 的 shell 服务最终还会执行一次 `app_process`。在定制 APatch 的安全模型中，普通 root shell 跨过这次 exec 后不能自动保留长期 Java daemon 所需的权限。表现可能是 daemon 启动即退出、读取 `/data/adb` 失败，或后续注入/控制通道不完整。

这与 Vendor Hook、IReZygisk 和 Zygisk Assistant 无关，也不应通过修改它们来绕过。

## 最终方案

`module/daemon` 按能力选择两条互不干扰的路径：

1. 定制 APatch：检测 `su --help` 是否提供 `--exec-context-privileged` 能力，然后执行：

   ```text
   su --no-pty -p --exec-context-privileged u:r:system_server:s0 -- \
       /system/bin/app_process64 -Djava.class.path=... ...
   ```

2. Magisk、KernelSU、未提供上述私有能力的上游 APatch：继续使用上游原生 `app_process` 启动方式。

所有参数都以独立 argv 传递，不经过 `su -c` 或拼接 shell 命令。优先选用 `app_process64`，不存在时才回退到 `app_process`。

## 隐藏与权限边界

- 没有新增专用 SELinux 域；使用已有的 `system_server` 域作为精确过渡目标。
- 没有设置 permissive。
- 没有添加全局 SELinux allow、修改共享 AVC 缓存或放宽其他进程。
- `--exec-context-privileged` 只把权限恢复给成功完成精确 exec 的 daemon 任务树。
- TEESimulator 原有 `sepolicy.rule` 保持不变，用于其自身 keystore 注入以及 Magisk/KernelSU 兼容；没有借本次适配扩大规则范围。
- APatch、KernelPatch、Vendor Hook、IReZygisk、Zygisk Assistant 的既有隐藏逻辑均未修改。

## 版本策略

- 定制版本名：`v4.0-ckb-apatch1`。
- 定制版本码：`40000 + 当前 Git 提交数`。
- 移除了指向上游 `dev` 的自动更新地址，防止 Root 管理器用官方包静默覆盖定制启动逻辑。

## 编译与安装

本项目的发布任务为 `zipRelease`，产物位于 `out/`，文件名包含定制版本名、版本码和 Git 短哈希。也可通过工作区统一脚本执行：

```text
python build_projects.py --project TEESimulator --type release
```

Windows 首次编译需要下载 Gradle 9.7。项目 Wrapper 使用已验证可访问的腾讯 Gradle 镜像，并为首次下载保留 120 秒连接超时与 3 次重试，避免 `services.gradle.org` 的 10 秒连接超时。

KeyMint、Android interfaces 和 frameworks/native 子模块使用中科大 AOSP 镜像；固定提交与上游 v4.0 完全相同，只替换下载入口，避免本机无法连接 `android.googlesource.com`。

CMake 选择 AIDL 时优先使用 Android SDK 中最新的 Build Tools，并识别 Windows 的 `aidl.exe`。若旧构建缓存仍记录不支持 `--min_sdk_version` 的 AIDL，会自动丢弃该缓存后重新选择，避免 Build Tools 30.0.3 抢在已安装的 36.x 前面。

Windows 版 AIDL 不会统一规范化 CMake 传入的输入文件与 `-I` 导入根，从而把同一目录误判为“不在 import paths”。配置阶段仅在 Windows 主机上把 AIDL 的输入文件和三个导入根全部转换为原生格式；Android/Linux 构建参数保持不变。

Windows 的 `PATH` 可能优先命中 `C:\Windows\System32\bash.exe`（WSL 启动器），该进程不能直接打开原生 CMake 传入的 `E:/.../rust/build.sh`。Windows 构建固定从 Git for Windows 的标准安装目录选择 `bash.exe`；Unix 主机仍从 `PATH` 选择 Bash。

工作区统一编译脚本会为 TEESimulator 选择 NDK 28.2，并把工作区内固定的 Cargo、Rustc 与 cargo-ndk 4.1.2 加入子进程环境；不依赖用户的系统 `PATH`。

本次代码修改没有执行编译、刷入或设备测试；由使用者自行完成。

## 不要重复踩的坑

- 不要只判断 `/data/adb/apd` 是否存在；旧版/官方 APatch 可能没有私有 bounded-exec 参数。
- 不要把整段 Java 命令塞进 `su -c`；这会多出 shell 解析层，破坏精确可执行文件与参数边界。
- 不要为 daemon 新建显眼的 permissive SELinux 域。
- 不要为了修 TEESimulator 去改 Vendor、IReZygisk 或全局模块脚本。
- 不要重新启用 TrickyStore 与 TEESimulator 同时 Hook keystore；上游安装脚本主动禁用 TrickyStore 是有意的冲突保护。
- 升级上游时必须重新核对 `module/daemon`，避免上游覆盖 APatch 专用分支。
